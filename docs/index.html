Hermes V3

Async Notification System in C++20 with Redis Broker & Observability

What is Hermes?

Hermes is a high-performance asynchronous notification backend built from scratch in C++20. It handles the same kind of system that sends order confirmations, password resets, and registration emails at scale. No frameworks, no ready-made abstractions — just clean, efficient C++ code.

V3 introduces:

  • Redis Pub/Sub broker alongside the internal in-process queue
  • Dual-pipeline architecture for side-by-side comparison
  • Prometheus metrics for observability
  • Docker Compose for reproducible deployment
  • Automated benchmarking with latency analysis

Architecture Evolution

From simple thread pool to distributed system:

V1: Basic Thread Pool

POST /notify ↓ Internal Queue (in-process) ↓ Thread Pool (4 workers) ↓ SMTP → MailBox

V2: Production-Ready

POST /notify ↓ validate + save DB (pending) ↓ PriorityEventQueue (CRITICAL first) ↓ Dispatcher ── RateLimiter (5 req/s) ↓ Thread Pool (4 workers) ├─ SMTP (send) │ ├─ SUCCESS → update status + metrics │ └─ FAIL → retry with exponential backoff │ └─ RetryScheduler (2^n backoff: 1s, 2s, 4s) └─ DLQ (Dead Letter Queue) after 3 retries

V3: Dual-Broker with Observability

POST /notify ├─ internal_queue.push(e) [V2 pipeline] └─ redis.PUBLISH(e) [NEW: external broker] Dispatcher A (Internal) Dispatcher B (Redis) ↓ ↓ Pool_Internal (4 workers) Pool_Redis (4 workers) ↓ ↓ [SMTP] → metrics_internal [SMTP] → metrics_redis │ │ └─────────────────────────────┘ ↓ GET /metrics/prometheus → Prometheus ↓ Grafana (visualization)

Why Redis? Thread Pool vs External Broker

Metric Thread Pool (Internal) Redis (External)
Latency P50 ~0.1–0.5ms ~1–2ms
Latency P99 ~1–2ms ~5–10ms
Throughput Very High High
Persistence ❌ Lost on crash ✅ Survives crashes
Multi-process ❌ Single process only ✅ Scales across processes
Complexity Low Medium (network overhead)
Dependencies ✅ Zero external deps ❌ Redis required
Design Decision: Both pipelines coexist in V3 — not as a replacement, but as a demonstration of trade-offs. Internal queue wins on latency and simplicity; Redis wins on durability and scalability.

Getting Started

Quick Start with Docker Compose

git clone https://github.com/JeanCassiano/hermes-cpp.git
cd hermes-cpp
docker-compose up

This starts:

  • Hermes at http://localhost:8080
  • Redis at localhost:6379
  • MailHog (email UI) at http://localhost:8025
  • Prometheus at http://localhost:9090
  • Grafana at http://localhost:3000 (admin / admin)

Sending a Notification

curl -X POST http://localhost:8080/notify \
  -H "Content-Type: application/json" \
  -d '{"type":"order_confirmed","email":"user@example.com","priority":"critical"}'

Response:

{"status": "queued", "id": 1, "event": "order_confirmed"}

View Emails (MailHog)

Since both pipelines process the same event, each notification is sent twice (intentional for V3 comparison).

Open MailHog

Check Metrics

curl http://localhost:8080/metrics | jq

Prometheus Format

curl http://localhost:8080/metrics/prometheus

Run Benchmark

python3 benchmark/bench.py \
  --url http://localhost:8080 \

  --output docs/results.json

Design Decisions

Why C++?

C++ gives you explicit control over performance: no garbage collection pauses, minimal memory overhead, and you can reason about exactly what the CPU is doing. For a system handling millions of notifications, that control matters.

Why SQLite?

SQLite is battle-tested, zero-configuration, and fits on disk. No separate database server needed for a notification system — but the code is generic enough to swap it out for PostgreSQL if needed.

Why Both Pipelines?

The internal thread pool is a valid production choice: low latency, zero network overhead, simple deployment. Redis adds durability and cross-process scalability. By running both, we can show the real trade-offs — not as marketing, but as side-by-side measurements.

Why Dual Dispatchers?

Each pipeline is completely isolated: separate ThreadPool instances, separate Metrics, separate processing logic. This shows the architectural cost/benefit of each broker strategy without interference.

Why Exponential Backoff?

If a downstream SMTP server is flaky, retrying immediately hammers it. Exponential backoff (1s, 2s, 4s) gives the server time to recover while still being aggressive early on.

API Reference

POST /notify

Enqueue a notification for delivery (published to both brokers).

{
  "type": "order_confirmed",
  "email": "user@example.com",
  "priority": "critical"
}

priority can be: critical, high, normal (default)

GET /events

List all events and their status (pending / sent / failed).

GET /events/:id

Details of a single event, including timestamps and retry count.

GET /dlq

Dead Letter Queue — events that exhausted all retries.

POST /dlq/:id/retry

Re-enqueue a dead-lettered event (resets retry_count to 0).

GET /metrics

Returns JSON with metrics for both pipelines.

GET /metrics/prometheus

Returns Prometheus text format (scraped by Prometheus at 5s intervals).

GET /health

Returns ok if the server is alive.

DELETE /events

Clears all events and DLQ (dev only).
